# バックエンドの設計方針

## プロジェクトとフォルダー

アプリ本体は既存の Web 用 `.csproj` ひとつを基本とし、テストは既存のテストプロジェクトに置く。Web プロジェクトでは `Features/<機能名>/` に、エンドポイント、業務処理、クエリ、業務型をまとめる。ファイルが少ないうちは機能フォルダー直下に置き、規模に応じて機能内を役割で分ける。独立した配布や別アプリからの再利用など、プロジェクトを分ける具体的な要件がある場合は、分割前に理由と影響を確認する。

| 役割 | 責務 |
|---|---|
| Controller | HTTP の入力を検証し、Service を呼ぶ。ユースケース単位のトランザクション境界と HTTP 応答を管理する。 |
| Service | 業務ルール、業務上の入力チェック、ユースケースの処理を担当する。必要に応じて EF Core や Repository を使う。 |
| Repository | 複数の Service で再利用するクエリや、複雑な検索・永続化処理をまとめる。 |
| Core | HTTP やデータアクセスに依存しない業務型、値の制約、共通の業務ルールを置く。 |

既存の Minimal API を使う機能では、エンドポイントが Controller と同じ役割を持つ。単純な処理には既存の型や EF Core の機能を使い、インターフェイスや共通基底クラスは具体的な用途があるときに追加する。

## EF Core とトランザクション

- 主キーでの取得や条件なしの単純な読み取りは、Service から EF Core の `DbContext` を直接使ってよい。件数が増えうる一覧では、取得件数を制限する。クエリの再利用や複雑さが Repository にまとめる判断基準になる。
- 読み取りだけの処理や、単一の `SaveChangesAsync` で完結する更新は、通常は明示的なトランザクションを開始しない。複数の書き込みや Service 呼び出しを一括で確定する必要があるときは、Controller 側で境界を決める。
- 同じトランザクションに含める Service と Repository は同じ `DbContext` を使う。Controller が成功時にコミットし、失敗時にロールバックされるようにする。配下では独自にトランザクションを開始・コミットしない。
- 再試行を有効にしている場合は、明示的なトランザクション全体を実行戦略の単位にする。外部 API などの副作用を含む場合は、失敗時や再試行時にどう扱うかを先に決める。

## 着手前に確認すること

既存仕様とコードで判断できる項目は読み取る。以下から、回答によって設計や受入条件が変わる未確定事項だけを確認する。

- 利用者と権限、入力の必須・任意・上限、業務上のエラー条件と表示。
- 既存 API・画面・データとの互換性、DB 変更や移行の要否、DB プロバイダーが未定ならその選択。
- どの更新を一括で成功・失敗させるか。同時更新、重複送信、再試行をどう扱うか。
- 想定件数・同時利用数、一覧の並び順とページング、測定すべき性能条件。
- 受入条件をどの単体テスト・結合テスト・操作確認で検証するか。
